# OpenServiceNOW Roadmap

## Principles

The roadmap is incremental. A phase is not considered complete because skeleton files, empty endpoints, static mock UI, or placeholder implementations exist.

For runtime phases, completion requires applicable code, migrations, API behavior, RBAC, tenant isolation, UI, tests, documentation, and end-to-end verification.

Priority order when starting any work session:

1. broken build or application startup,
2. migration/database failures,
3. security defects,
4. regressions,
5. work explicitly marked IN PROGRESS,
6. missing tests for critical existing behavior,
7. remaining work in the active phase,
8. next phase,
9. refactoring that is justified by concrete problems.

## Phase 0 — Architecture

Goal: establish architecture, boundaries, implementation order, and project state tracking before runtime implementation.

Deliverables:

- repository analysis,
- target architecture for Go + MySQL,
- modular-monolith boundaries,
- data-access and transaction strategy,
- multi-tenancy and RBAC architecture,
- worker/scheduler/event architecture,
- frontend architecture,
- security/performance/testing principles,
- ROADMAP.md,
- TODO.md,
- STATUS.md,
- CHANGELOG.md,
- architecture ADRs.

Exit criteria:

- architecture documents are internally consistent,
- runtime work is clearly separated into later phases,
- no nonexistent runtime feature is represented as complete,
- next implementation tasks are explicit.

- Redis connectivity,
- migration runner,
- Docker Compose for MySQL and Redis,
- health/readiness checks,
- development Makefile.

Identity/security foundation:

- tenants,
- local users,
- password hashing,
- authentication session/token strategy,
- groups,
- roles,
- permissions,
- scoped assignments,
- backend authorization middleware/service,
- audit foundation.

Testing:

- unit test baseline,
- `httptest`,
- MySQL integration test harness,
- tenant isolation tests,
- RBAC tests,
- startup/configuration tests.

Exit criteria:

- dependency lock files are generated by real Go/npm dependency resolution and committed,
- local development environment is reproducible,
- API starts and shuts down correctly,
- database migrations apply, one-step rollback, fully rollback and re-apply cleanly,

- Redis readiness and rate-limit failure behavior are verified,
- backend format/vet/unit/race/build and MySQL integration suites pass,
- frontend typecheck/unit/build pass,
- full-stack Playwright passes against the real API, MySQL and Redis on desktop and a mobile viewport,
- no CI/runner blocker remains.

## Phase 2 — Work Platform Foundation

Goal: implement the reusable work-record, asynchronous execution, event, attachment and activity capabilities required by ITSM domains before Incident Management is introduced.

### Phase 2A — Shared work-record primitives

Deliverables:

- concurrency-safe business numbering,
- assignment and assignment-group model,
- comments and work notes with explicit visibility semantics,
- watchers,
- status/history primitives,
- related-record links,
- optimistic locking,
- reusable list/filter/cursor-pagination contracts,
- bounded bulk-operation contracts,
- stable task/reference identifiers without forcing every domain into one universal business table.

### Phase 2B — Durable jobs and worker

Deliverables:

- persistent job table and attempt history,
- states `QUEUED`, `RUNNING`, `RETRYING`, `COMPLETED`, `FAILED`, `CANCELLED`,
- job type, tenant, payload, result, progress, error and retry metadata,
- `cmd/worker` with bounded concurrency, context cancellation and graceful shutdown,
- claim/lease semantics that survive process restarts,
- idempotency-aware retry policy,
- cancellation,
- per-job execution logs/diagnostics that do not expose secrets,
- worker health and operational metrics.

### Phase 2C — Domain events and transactional outbox

Deliverables:

- stable versioned event envelope,
- transactional `outbox_events` persistence,
- event type, tenant, aggregate type/id, payload and creation metadata,
- worker-driven delivery with retry and idempotency,
- initial in-process subscribers behind an abstraction that does not bind domain code to a permanent broker implementation,
- event contracts for task lifecycle changes,
- tests proving a committed business write cannot lose its required asynchronous event.

### Phase 2D — Attachments and activity timeline

Deliverables:

- attachment metadata separated from business records,
- storage abstraction suitable for local development and later object storage,
- file size, MIME/type and filename validation,
- checksum/integrity metadata,
- tenant/RBAC authorization for upload/download/delete,
- safe storage paths and download headers,
- activity timeline projection combining comments, work notes, assignment/status transitions, attachments and selected audit/domain events,
- cursor pagination for large timelines.

Exit criteria:

- common services are reusable by Incident, Request, Change and Problem without a fragile universal business table,
- jobs survive worker restart and cannot be processed concurrently beyond their claim semantics,
- retry/cancellation behavior is deterministic and audited,
- transactional outbox integration is verified under rollback and retry scenarios,
- attachment access cannot cross tenant or authorization boundaries,
- activity timeline is deterministic and paginated,
- cross-tenant and concurrent-operation tests pass,
- Phase 3 can consume these services without reimplementing its own jobs, events, comments, attachments or timeline.

## Phase 3 — Incident Management

Core process delivered in PR #17: model/migrations, create/read/update/list, active assignment, category/subcategory catalog, explicit priority matrix/override, backend lifecycle, object RBAC/read-own, idempotency/versioning and agent/reporting UI with real worker history. This is the first complete business process, not completion of every extension below. PR #18 extends the process with public replies/internal notes, files, filtered activity, observers, related/parent-child records and two controlled operator batch actions. CMDB/service fields wait for a real data source; templates and major-incident orchestration remain future work. This does not mark all advanced bulk/workflow capabilities delivered. Verification evidence is maintained in STATUS.md.

Goal: production-capable incident lifecycle.

Deliverables:

- incident data model and migrations,
- create/read/update/list,
- assignment and assignment groups,
- impact/urgency/priority,
- status lifecycle,
- categories/subcategories,
- reporter/requester,
- service/CI relations,
- parent/child incidents,
- major incident flag/workflow foundation,
- comments/work notes/attachments/timeline integration,
- templates,
- bulk actions,
- agent UI.

Exit criteria:

- complete API/UI flow,
- lifecycle transitions enforced on backend,
- RBAC and tenant isolation tested,
- optimistic locking handles concurrent updates,
- list queries avoid N+1 behavior.

## Post-15 evolution

Potential later work should be driven by evidence rather than pre-created complexity:

- selective service extraction,
- external event broker,
- OpenSearch/Elasticsearch if MySQL search is insufficient,
- dedicated analytics store,
- multi-region deployment,
- advanced service mapping,
- discovery agents,
- AIOps capabilities,
- mobile-specific clients.

Each material architectural shift requires an ADR.
