# OpenServiceNOW Roadmap

## Module 08 — delivered runtime scope

Tenant incident process configuration and Major Incident coordination are implemented with API, UI, durable communication/reminders, independent child outcomes and shared workspace actions/review. See [the module guide](docs/incidents.md) for configuration, local evidence and product boundaries. Problem Management, Change Management and external alert ingestion remain separate modules; typed integration contracts are available.


## Principles

The roadmap is incremental. A phase is not considered complete because skeleton files, empty endpoints, static mock UI, or placeholder implementations exist.

For runtime phases, completion requires applicable code, migrations, API behavior, RBAC, tenant isolation, UI, tests, documentation, and end-to-end verification.

Priority order when starting any work session:

1. broken build or application startup,
2. migration/database failures,
3. security defects,
4. regressions,
5. work explicitly marked IN PROGRESS,
6. missing tests for critical existing behavior,
7. remaining work in the active phase,
8. next phase,
9. refactoring that is justified by concrete problems.

## Phase 2 — Work Platform Foundation

Goal: implement the reusable work-record, asynchronous execution, event, attachment and activity capabilities required by ITSM domains before Incident Management is introduced.

### Phase 2A — Shared work-record primitives

Deliverables:

- concurrency-safe business numbering,
- assignment and assignment-group model,
- comments and work notes with explicit visibility semantics,
- watchers,
- status/history primitives,
- related-record links,
- optimistic locking,
- reusable list/filter/cursor-pagination contracts,
- bounded bulk-operation contracts,
- stable task/reference identifiers without forcing every domain into one universal business table.

### Phase 2B — Durable jobs and worker

Deliverables:

- persistent job table and attempt history,
- states `QUEUED`, `RUNNING`, `RETRYING`, `COMPLETED`, `FAILED`, `CANCELLED`,
- job type, tenant, payload, result, progress, error and retry metadata,
- `cmd/worker` with bounded concurrency, context cancellation and graceful shutdown,
- claim/lease semantics that survive process restarts,
- idempotency-aware retry policy,
- cancellation,
- per-job execution logs/diagnostics that do not expose secrets,
- worker health and operational metrics.

### Phase 2C — Domain events and transactional outbox

Deliverables:

- stable versioned event envelope,
- transactional `outbox_events` persistence,
- event type, tenant, aggregate type/id, payload and creation metadata,
- worker-driven delivery with retry and idempotency,
- initial in-process subscribers behind an abstraction that does not bind domain code to a permanent broker implementation,
- event contracts for task lifecycle changes,
- tests proving a committed business write cannot lose its required asynchronous event.

### Phase 2D — Attachments and activity timeline

Deliverables:

- attachment metadata separated from business records,
- storage abstraction suitable for local development and later object storage,
- file size, MIME/type and filename validation,
- checksum/integrity metadata,
- tenant/RBAC authorization for upload/download/delete,
- safe storage paths and download headers,
- activity timeline projection combining comments, work notes, assignment/status transitions, attachments and selected audit/domain events,
- cursor pagination for large timelines.

Exit criteria:

- common services are reusable by Incident, Request, Change and Problem without a fragile universal business table,
- jobs survive worker restart and cannot be processed concurrently beyond their claim semantics,
- retry/cancellation behavior is deterministic and audited,
- transactional outbox integration is verified under rollback and retry scenarios,
- attachment access cannot cross tenant or authorization boundaries,
- activity timeline is deterministic and paginated,
- cross-tenant and concurrent-operation tests pass,
- Phase 3 can consume these services without reimplementing its own jobs, events, comments, attachments or timeline.

## Shared data dictionary and configurable forms (partial delivery)

The current worktree adds tenant-scoped, versioned metadata configuration for Incident and CI: typed custom values, configurable dictionaries and priority matrix, backend validation, published form/list layouts, permission-key presentation views, reference lookups, configuration history, locale preferences, catalog validation adapter and metadata-aware CI import. It includes a real administration screen and consumes published custom fields in Incident and CI forms and lists. See docs/metadata.md for APIs, migrations and the supported boundary.

This is a partial foundation, not a completed general-purpose App Engine or all-domain metadata platform. Runtime record adapters currently cover Incident and CI; team-specific views, field ACLs, arbitrary reporting/export, full-app localization and durable large backfills remain future work. Completion requires local Go unit/integration/race/vet/build checks, applying and rolling back migrations against isolated MySQL, EXPLAIN review for typed custom filters, and browser verification against the real API and database. Current environment limits are recorded in STATUS.md.
